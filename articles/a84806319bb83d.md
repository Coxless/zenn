## はじめに

前回の記事では、「AIでコードを書く速度は上がったのに、確認やレビューがボトルネックになっている」という課題感から、国内外のテックブログや論文、各社のアプローチを調べて整理しました。

<!-- 公開時に前回記事のリンクを貼る: https://zenn.dev/coxless/articles/a8c4e91f2b30d5 -->

調査を通じて一番強く感じたのは、**「AIが高速に生成する大量のコードを、人間がこれまでと同じように事後で1行ずつ目視チェックし続けるのは構造的に無理がある」**ということです。

そこで今回は、前回の調査で見えてきたキーワード（仕様駆動開発、ハーネスエンジニアリング、影響範囲によるトリアージ、動作の証拠など）を組み合わせて、**「自分ならこれからの開発・コードレビューのプロセスをどう設計するか」**を自分用のガイドラインも兼ねてまとめてみました。

---

## 基本方針：人間は「事後の間違い探し」から「事前の枠組み作り」へ回る

まず大前提として、人間の主な役割を「書かれたコードの間違い探し（事後検査）」から**「AIが道を外れないための枠組み作り（事前設計）」**へとシフトさせます。

```text
【従来の役割】   [コード記述] ──▶ [事後コードレビュー (人間の主業務)]
【AI時代の役割】 [仕様定義 (Spec) & ハーネス構築 (人間の主業務)] ──▶ [AI生成 & 自動検証]
```

具体的には、次の3つを基本方針にします。

1. **仕様（Spec）を正にする（Spec-Driven Development）**
   いきなりAIにコードを書かせるのではなく、「目的・やらないこと（Out-of-scope）・制約条件・受け入れ基準」を短くても先に定義します。人間が一番時間を割くべきなのは、出てきたコードの添削ではなく「最初の仕様のすり合わせ」です。
2. **ハーネス（機械的な制約の壁）を整える（Harness Engineering）**
   レビューで人間が毎回同じような指摘をするなら、それは人間の仕事ではなく仕組みの不備と捉えます。`AGENTS.md`（または `CLAUDE.md`）への明文化だけでなく、型、Linter、アーキテクチャテスト（Semgrep等）で機械的に弾く壁を作ります。
3. **人間が最後まで手放さない判断を絞る**
   すべてを目視するのをやめる代わりに、以下の3点だけは人間が責任を持って判断します。
   - プロダクトの意図やビジネス要件と合っているか
   - 長期的な設計のシンプルさが保たれているか（不要に複雑な抽象化が混ざっていないか）
   - 不可逆なリスク（認証・認可、決済、データ構造変更、法規制など）の最終承認と責任

## 設計1：変更の「爆発半径（Blast Radius）」でレビューを3段階に分ける

すべてのPR（プルリクエスト）を同じ熱量でレビューするのをやめ、変更が壊れたときの**爆発半径（Blast Radius：影響範囲と可逆性）**に応じて、3つのTier（階層）に分流する設計にします。

```text
               ┌─▶ [ Tier 0: 低リスク ] ──▶ CI ＋ AIレビュー通過 ──▶ 自動マージ (0人承認)
               │
[ PR提出 ] ────┼─▶ [ Tier 1: 中リスク ] ──▶ CI ＋ AI一次下読み ────▶ 人間1名確認 (1人承認)
               │
               └─▶ [ Tier 2: 高リスク ] ──▶ CI ＋ AI監査レポート ──▶ 厳格審査 (複数人承認)
```

| 階層 | 対象となる変更の例 | 承認要件 | 人間の見方 |
|---|---|---|---|
| **Tier 0（低リスク）** | ドキュメント・コメント修正、型定義の追加、文言変更、フィーチャーフラグ裏の新機能、小規模な内部リファクタリング | **0人承認（自動マージ）** | 原則見ない。CIの全ゲート通過＋AIレビューでCritical指摘ゼロなら即時マージ |
| **Tier 1（標準リスク）** | 通常の機能追加、既存コンポーネントの修正、一般的なバグ修正 | **1人承認** | 1行ずつ精読しない。AIが生成した要約・影響範囲と「動作の証拠」を見て、仕様と合っているかだけ確認 |
| **Tier 2（高リスク）** | 認証・認可ロジック、決済・課金処理、DBスキーマ変更、コアアーキテクチャ変更、外部公開API | **複数人承認（または重点審査）** | AIの事前監査レポートを参考にしつつ、ドメイン把握者がコードの細部まで厳格に目視審査 |

ポイントは、**Tier 0 と Tier 1 で人間のレビュー工数を徹底的に節約し、浮いた認知リソースを Tier 2（本当に人間が頭を使うべき危険な変更）に集中投下する**ことです。

個人開発であっても、「この変更はTier 0だからテストが通ればそのままマージ」「ここはDBスキーマや認証に関わるTier 2だから自分で1行ずつしっかり読む」と線引きしておくだけで、確認疲れがかなり減るはずです。

## 設計2：AIレビューを「単発プロンプト」ではなく4段のパイプラインにする

「PRを作ったらとりあえずAIにレビューさせる」だけだと、どうでもいい細かい指摘（Nitpick）ばかりが並んでしまい、かえってノイズになることがよくあります。

そこで、検証プロセスを単一のAIプロンプトではなく、**4段階のパイプライン**として組むのが良さそうだと考えています。

```text
[ PR作成 / 差分生成 ]
     │
     ├──▶ Step 1. 決定論的ゲート (Lint / TypeCheck / SAST / Test) ──▶ (失敗時は即ブロック)
     │
     ├──▶ Step 2. 観点別マルチエージェント検証
     │             ├── Security Agent (脆弱性・権限抜け)
     │             ├── Architecture & Rule Agent (`AGENTS.md` / 設計規約)
     │             └── Test Coverage Agent (境界値・異常系テストの抜け)
     │
     ├──▶ Step 3. 動作の証拠 (Receipts) の添付 (テスト実行ログ / スクショ等)
     │
     └──▶ Step 4. トリアージ判定 & 人間向けの要点サマリー作成
```

### Step 1：決定論的ゲート（Deterministic Gates）を先に通す

型チェック、Linter、Formatter、SAST（静的セキュリティスキャン）、単体テストは100%機械的に判定できる領域です。ここをパスしないコードは、そもそもAIレビューや人間のレビューキューに到達させないようにします。

### Step 2：観点別のマルチエージェント検証

1つのプロンプトで「コード全体をレビューして」と頼むと指摘が浅くなりがちです。そのため、以下のように観点を絞ったサブエージェント（または複数の専門ツール）を並列で走らせます。

- **セキュリティ観点**：認証抜けやインジェクション、シークレット露出がないか
- **アーキテクチャ・規約観点**：`AGENTS.md` に書かれた設計ルールやレイヤー間の依存方向を守っているか
- **テスト観点**：ハッピーパスだけでなく、境界条件や異常系のテストが書かれているか

また、コードを書いたAIと同じモデルだけでレビューさせると同じ盲点を見逃す（Self-Review Bias）ため、可能であれば実装とは別のモデルや別ツールを組み合わせるのが理想的です。

### Step 3：「動作の証拠（Receipts）」の提出を義務づける

AIエージェントの「テストを通しました」「動作確認済みです」という自己申告はそのまま信用せず、**客観的な「動作の証拠（Receipts）」**をPRや作業報告に必ず残させます。

- 実際に実行したテストコマンドと、その標準出力ログ
- APIレスポンスの実例
- UI変更であればスクリーンショットや操作キャプチャ

人間はコードのdiffを読む前にまずこの「証拠」を見ることで、「本当に動くのか？」を推測する認知コストをゼロにできます。

### Step 4：トリアージ判定と人間向けサマリー

変更ファイルパス（例：`auth/` や `migrations/` に触れているか）や変更行数をもとに Tier 0〜2 を判定し、人間が見る必要がある場合は「何が変わったか」「どこを重点的に見るべきか」の要約だけをコンパクトに出力させます。

## 設計3：いきなり全部やらず、4フェーズで段階的に導入する

最初から「Tier 0 の自動マージ解禁」まで一気にやろうとすると、ガードレールが足りない状態で壊れたコードが混入してしまいます。実際のプロジェクトに導入するなら、以下の4つのフェーズで段階的に進めるのが現実的だと考えています。

```text
Phase 1: CI決定論的ゲートの100%徹底
   │
Phase 2: PRサイズの小粒化 (200〜400行目安に制限)
   │
Phase 3: AI一次スクリーニング & `AGENTS.md` / Linterへの還流ループ構築
   │
Phase 4: Tier 0 (低リスク) の Auto Merge 解禁
```

### Phase 1：CI決定論的ゲートの100%徹底

まずは型チェック・Lint・テストのCIパスを必須化し、これが通っていない状態のコードは人間が一切見ないルールを徹底します。あわせて、SemgrepやカスタムLintルールで「絶対に破ってほしくないアーキテクチャ制約」を機械化します。

### Phase 2：PRサイズの小粒化

AIにまとめて実装させると、平気で1,000行を超えるPRが作られます。しかしPRが大きくなると、AIレビューの精度も人間の注意力も急激に落ちます。
変更行数は**200〜400行程度**を目安に制限し、タスクを小さく分割してPRを出させる運用を定着させます。

### Phase 3：AI一次スクリーニングと「フィードバックループ」の構築

AIによるPRの自動下読み・要約・一次指摘を導入します。
ここで一番大事なのが、**「人間がレビューで指摘した内容を、その場限りで終わらせないこと」**です。人間が「こう書いてほしい」と指摘したら、必ずそれを `AGENTS.md` のルール追記やLinterの設定に書き戻し、同じ指摘を二度としなくて済むようにハーネスを育てていきます。

### Phase 4：Tier 0（低リスク）の Auto Merge 解禁

Phase 1〜3 によって「CIとAIレビューを通れば致命的な問題は起きない」という信頼が貯まった段階で、ドキュメント修正や軽微な変更（Tier 0）から順次「人間の承認なしでの自動マージ」を解禁していきます。

## うまくいっているかを測る指標

AIを導入した開発では、「書いたコード行数」や「作成したPR数」はいくらでも水増しできるため、生産性の指標としては機能しなくなります。代わりに、次のような指標で健全性を見るのが良さそうです。

| 指標 | 見るべきポイント | 目安・方向性 |
|---|---|---|
| **欠陥流出率（Escaped Defects）** | レビューをすり抜けて本番環境で発生した不具合の件数 | 自動化を進めてもここが増えないことが大前提 |
| **レビューリードタイム** | PR作成からマージされるまでの待ち時間 | ボトルネックが解消されているか（数時間以内が理想） |
| **Tier 0 自動マージ率** | 全PRのうち、人間の目視なしでマージできた割合 | ハーネスが育つほど自然に上がっていく（30〜50%など） |
| **PRあたりの認知的負荷** | レビューするときに「しんどい・意味が分からない」と感じる度合い | 小粒化とReceipts添付で下がっているか |

## おわりに

2記事にわたって、AI時代のコードレビューに関する世の中の事例調査と、それを踏まえた自分なりの設計案を整理してみました。

要点を振り返ると、結局のところ**「いかに人間が事後でコードを読まなくて済む状態を、事前の仕様（Spec）と機械的な制約（ハーネス）で作れるか」**に尽きるのかなと思っています。

まずは自分自身の開発リポジトリで、以下の3つから実際に取り入れて試してみるつもりです。

1. AIに実装させる前に、短いSpec（目的・スコープ外・検証方法）を書き出す
2. 作業完了時には必ず「動作の証拠（テスト実行ログ等）」をセットで出させる
3. 自分で手直し・指摘した箇所は、その都度 `AGENTS.md` やLinterルールに還元する

実際に運用してみてうまくいったことや、逆につまずいたところがあれば、また別の記事で共有したいと思います。もし「自分のところではこうやっている」「このツールやルールが効いた」といった知見があれば、ぜひコメントで教えてください！
