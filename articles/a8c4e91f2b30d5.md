## はじめに

Claude Codeなどのコーディングエージェントを日常的に使うようになり、コードを書く速度はかなり上がりました。一方で、生成されたコードの差分（diff）を確認したり、問題がないかレビューしたりする時間がボトルネックになっていると感じることが増えています。

自分で書いたコードなら「なぜこう書いたか」が頭に入っていますが、AIが一瞬で出力した数百行のコードを読むのは想像以上に頭を使います。

「世の中のエンジニアや開発組織はこの問題にどう向き合っているんだろう？」と思い、国内外のテックブログや論文、議論などを集めて調べてみました。

今回はまず**「調査・整理編」**として、なぜAI時代にコードレビューが詰まるのか、そして先行する組織がどのようなアプローチをとっているのかをまとめます（次回、これを踏まえて自分の開発環境にどう落とし込むかを書く予定です）。

## なぜAI時代にコードレビューがボトルネックになるのか

調べてみると、個人の感覚だけでなく、多くの組織や定量調査でも「ボトルネックがコード記述からレビューへ移動した」ことが指摘されていました。

### 1. 「生産性のパラドックス」の発生

AIコーディングツールの導入によって、開発者1人あたりのコード生成量やPR（プルリクエスト）の提出数は30〜40%以上増加しているというデータがあります。

ところが、Harvard大学などの調査やThe Pragmatic Engineer等で紹介されているデータを見ると、**最終的にリリースされた機能価値（完了したチケット数など）はほぼ横ばい**にとどまり、代わりに**PRのレビュー待ちリードタイムが150%〜440%に膨れ上がる**という現象が起きています。

```text
【従来の開発プロセス】
[仕様策定] ──▶ [コード記述 (遅い/高コスト)] ──▶ [コードレビュー (追いつく)] ──▶ [出荷]

【AI導入後のボトルネック移動】
[仕様策定] ──▶ [AIコード生成 (高速/安価)] ──▶ [★コードレビュー (極度の渋滞)] ──▶ [出荷]
```

上流の「書く速度」だけが上がった結果、下流の「人間が読んで検証する工程」が詰まり、開発プロセス全体のスループットが上がらないという構造です。

### 2. レビュアーが「世界で最初にそのコードを読む人間」になる

単にPRの数が増えただけでなく、**AIが生成したコード特有の読みづらさ（認知的負荷の高さ）**も大きな要因として挙げられていました。

| 課題 | 内容 |
|---|---|
| **意図の欠落（Missing Intent）** | 人間が書いたコードと違い、「なぜこの実装を選んだのか」という背景が存在しない。PR作成者自身も細部を把握していないことがあり、レビュアーが「世界で最初にそのコードを解読する人間」になる |
| **一見正しそうに見える（Hallucinated Correctness）** | フォーマットが綺麗に整っていて簡単なテストも通るため、パッと見の完成度が高い。しかし境界条件の抜けや意図しない例外処理が紛れ込んでいることがある |
| **Code Smellsの沈殿** | AI生成コードに関する大規模な実証研究（arXiv）によると、AIが作り込む問題の約89%はバグではなくCode Smells（保守性の低下や冗長な記述）であり、その約23%が修正されずにリポジトリに残り続ける |
| **疲労によるゴム印化（Rubber Stamping）** | 大量の綺麗なコードを読み続けることでレビュアーが認知的に疲弊し、「たぶん動くだろう」と精査を諦めてLGTMを出してしまうリスクが高まる |

特に「レビュアーが世界で最初にそのコードをちゃんと読む人間になる」という指摘は、自分の体験と照らし合わせてもかなり腑に落ちました。

## 自動化できる領域と、越えられない4つの壁

「人間が読むのが大変なら、レビュー自体もAIに任せればいいのでは？」と考えるのが自然です。ただ、いろいろな記事やベンチマーク調査を読んでいくと、**機械やAIに任せられる領域**と**どうしても人間に残る領域**の境界線がはっきり分かれていました。

| レイヤー | 性質 | 具体例 |
|---|---|---|
| **1. 決定論的（Deterministic）ゲート** | 100%機械化できる | 型チェック、Linter、Formatter、SAST（静的セキュリティ解析）、単体テストのパス |
| **2. 確率的スクリーニング（AIレビュー）** | AIで一次チェック・補助ができる | PRの要約、変更影響の洗い出し、典型的なバグや規約違反の指摘、テストケースの不足指摘 |
| **3. 人間による高次判断** | 自動化が難しい | ドメイン文脈の妥当性、仕様自体の正しさ、長期的な設計のシンプルさ、最終責任 |

AIレビューツール自体の精度も上がっていますが、それでも**自動化が越えられない壁**として以下の4つがよく挙げられています。

1. **リポジトリ固有の暗黙知・歴史的経緯**
   コードベース上に明文化されていない過去の経緯や、組織特有のドメイン知識の解読。
2. **同種モデル間のバイアス（Self-Review Bias）**
   コードを生成したAIと同系統のモデルにレビューをさせると、同じ盲点（ブラインドスポット）を共有してしまい、間違いを「正しい」とスルーしやすい。
3. **「間違った仕様通りに正しく動くコード」の判定**
   コードが仕様通りに動いていても、その仕様自体がビジネスやプロダクトの意図とズレていないかは、コードの差分だけ見ても判定できない。
4. **最終的な責任（Accountability）**
   本番障害が起きたときや、セキュリティ・法規制上の問題が発生したとき、AIは責任を取れないため、最終的な承認責任は人間側に残る。

## 先行する組織はどう解決しているか（4つのアプローチ）

では、実際にAIを活用している国内外の開発組織はどうやってこの「レビュー渋滞」を乗り越えているのでしょうか。

各社の事例を整理してみると、「AIへの委譲度」と「人間が介入するタイミング（事前か事後か）」によって、大きく**4つのアプローチ**に分類できました。

```text
【AIへの委譲度と人間の介入タイミングによる4分類】

       高 ┌────────────────────────────────────────────────────────┐
          │  ① 完全自動化・Auto Merge推進型                       │
          │   ・事例: Findy (85%自動マージ), Semgrep など          │
          │   ・特徴: 事前にSpec/テストを固定し、条件合致で0人承認 │
  A       ├────────────────────────────────────────────────────────┤
  I       │  ② リスクベース・トリアージ分流型                     │
  委      │   ・事例: Anthropic (Claude Codeチーム), Amazon など   │
  譲      │   ・特徴: 影響範囲に応じ Tier 0(自動)〜2(複数人)へ分流 │
  度      ├────────────────────────────────────────────────────────┤
          │  ④ マルチエージェント相互検証型                       │
          │   ・事例: PostHog (qa-swarm) など                      │
          │   ・特徴: 専門AIが相互検証し、残った論点のみ人間へ回す │
          ├────────────────────────────────────────────────────────┤
          │  ③ 二段階スクリーニング型                             │
          │   ・事例: LINEヤフー, atama plus, PLAID, FIXIT など    │
          │   ・特徴: AIが事前に要約・下読み・指摘、人間が最終判断 │
       低 └────────────────────────────────────────────────────────┘
          事前（仕様定義・制約の構築） ────────▶ 事後（マージ直前）
                         人間の主たる介入タイミング
```

| アプローチ | 人間の目視介入度 | 主な特徴 | 代表的な言及・採用事例 |
|---|---|---|---|
| **① 完全自動化・Auto Merge型** | 原則なし（0人承認） | 可逆な変更であれば、事前の仕様・CIテスト・動作の証拠を条件に自動マージ | Findy、Semgrep |
| **② リスクベース・トリアージ型** | 0人〜複数人（可変） | 変更の影響範囲（Blast Radius）に応じて自動マージと厳格審査を分流 | Anthropic（Claude Codeチーム）、Amazon |
| **③ 二段階スクリーニング型** | 最終判断のみ（要点確認） | AIが事前に下読み・要約・一次指摘を行い、人間は設計や仕様適合性のみ判断 | LINEヤフー、atama plus、PLAID、FIXIT |
| **④ マルチエージェント検証型** | 例外・難問のみ | 観点別の専門AIが並列検証し、AI間で解決できない論点のみ人間に昇格 | PostHog |

それぞれの特徴をもう少し詳しく見てみます。

### ① 完全自動化・Auto Merge推進型

「人間がマージ前に1行ずつ読む」という前提自体を手放し、CIの決定論的ゲートとAIレビューをパスしたPRは**人間の承認なし（0人承認）で自動マージする**アプローチです。

国内でもFindy Engineer Labの記事で「PRの約85%を自動マージしている」という事例が紹介されており、かなりインパクトがありました。もちろん何でも無条件にマージするわけではなく、「事前に仕様やテストが固まっていること」「問題があってもすぐに切り戻せる（可逆である）こと」を前提に、事後チェックよりもリードタイム短縮と事前制約に振り切る考え方です。

### ② リスクベース・トリアージ分流型

すべてのPRを同じ重さでレビューするのをやめ、変更の**爆発半径（Blast Radius：壊れたときの影響範囲）**によってレビューのルートを分けるアプローチです。AnthropicのClaude Codeチームなどの事例がこの形に近いです。

```text
               ┌─▶ [ Tier 0: 低リスク ] ──▶ CI ＋ AIレビュー通過 ──▶ 自動マージ (0人承認)
               │
[ PR提出 ] ────┼─▶ [ Tier 1: 中リスク ] ──▶ CI ＋ AI一次下読み ────▶ 人間1名確認 (1人承認)
               │
               └─▶ [ Tier 2: 高リスク ] ──▶ CI ＋ AI監査レポート ──▶ シニア厳格審査 (複数人承認)
```

- **Tier 0（低リスク）**：ドキュメント修正、型定義の追加、文言変更、フィーチャーフラグ裏の変更などは人間が見ずに自動マージ
- **Tier 1（中リスク）**：通常の機能追加やバグ修正は、AIの要約を使って人間1人が素早く確認
- **Tier 2（高リスク）**：認証・認可、決済処理、DBスキーマ変更、コアアーキテクチャの変更など「不可逆で影響が大きい変更」にだけ、人間のレビュアーのリソースを集中投下する

人間の認知リソースには限りがあるため、「本当に人間が見るべき危険な変更」にだけ集中するというのは非常に合理的だと感じました。

### ③ 二段階スクリーニング型

日本のテック企業のブログ（LINEヤフー、atama plus、PLAID、FIXITなど）で特に多く見られたのが、現実的かつ導入しやすいこのアプローチです。

人間がいきなり生のdiffを読むのではなく、まずAIがPRの要約・変更の意図・影響範囲・一次指摘（下読み）を作成し、人間はそれをガイドにして「仕様と合っているか」「設計として無理がないか」の最終判断に集中します。

また、atama plusやPLAIDの事例で印象的だったのは、レビューを「する側」の効率化だけでなく、**レビュー「される側（PRを出す側）」の工夫**もセットで行っている点です。
- AIにコードを書かせると巨大PRになりがちなので、PRを小さく分割する
- AIとやり取りした背景や「何を意図して生成させたか」のコンテキストをPRに添える
といった運用の見直しが、結果的にレビュアーの認知負荷を大きく下げていました。

### ④ マルチエージェント相互検証型

1つのAIモデルによるレビューの限界（見落としやバイアス）を突破するため、**観点ごとに専門化した複数のAIエージェント**を並列で走らせるアプローチです。

たとえばPostHogの事例（`qa-swarm`）などでは、セキュリティ観点、アーキテクチャ規約観点、テスト網羅性観点など複数のエージェントや異なるモデルを組み合わせて検証させ、さらには「実装したエージェントとは別のエージェントに意地悪なテストケースで攻撃させる（敵対的検証）」といった工夫が紹介されています。そこで残った曖昧な論点や設計判断だけを人間に回す仕組みです。

## 調査から見えてきた3つの重要キーワード

4つのアプローチのどれをとるにしても、共通して繰り返し登場していたキーワードが3つありました。今後の開発プロセスを考える上で核になりそうな概念です。

### 1. シフトレフトと仕様駆動開発（Spec-Driven Development）

これまでのコードレビューは「コードが書かれた後」に人間が介入する事後検査でした。しかしAI時代には、人間の主な仕事を**「コードを書かせる前の仕様定義（Spec）と検証基準の策定」**へ前倒し（シフトレフト）していく必要があります。

```text
【従来の役割】   [コード記述] ──▶ [事後コードレビュー (人間の主業務)]
【AI時代の役割】 [仕様定義 (Spec) & ハーネス構築 (人間の主業務)] ──▶ [AI生成 & 自動検証]
```

仕様駆動開発（SDD）では、目的・スコープ外（Out-of-scope）・制約条件・受け入れ基準を明文化した「仕様（Spec）」を唯一の正（Source of Truth）とし、コード自体はそこから生成される「中間表現」に近いものとして扱います。人間はコードの細部ではなく、仕様のレビューに時間を割くという考え方です。

### 2. ハーネスエンジニアリング（Harness Engineering）

コードレビューで人間が毎回「この書き方は規約違反」「この層からDBを直接呼ばないで」と指摘するのは非効率です。代わりに、AIが最初から設計違反を起こせないような**機械的制約の壁（ハーネス）**を整備するアプローチが「ハーネスエンジニアリング」と呼ばれています。

具体的には以下のようなものを組み合わせます。

- `AGENTS.md` や `CLAUDE.md` へのルール明文化（ただしプロンプトだけでは100%は守られない）
- 厳格な型システムとLinter
- SemgrepやArchUnitなどを使った**アーキテクチャテスト**（依存方向の違反などを機械的に弾く）
- レビューで人間が指摘した内容を、その都度Linterルールや `AGENTS.md` に書き戻すフィードバックループ

### 3. 「動作の証拠（Receipts）」の提出

コーディングエージェントを使っていると、AIが「テストを実行して問題ないことを確認しました」と報告してきたのに、実際にはテストが動いていなかったり、モックでごまかされていたりすることがあります。

そのため、コードの差分（diff）だけを見て良し悪しを判断するのではなく、**実際のテスト実行ログ、コマンド出力、UIのスクリーンショットや動画などの「動作の証拠（Receipts）」**をPRに自動添付させ、人間はその証拠を確認するというプラクティスが重視されるようになっています。

## おわりに

「AIでコードを書くのは速くなったのに、確認やレビューで詰まる」という個人的な課題感から調べ始めましたが、国内外の多くの組織がまったく同じ壁にぶつかっており、**「人間がマージ前に1行ずつ全部読む」という前提そのものを再設計し始めている**ことが分かりました。

特に以下のポイントは、チーム開発だけでなく個人のエージェント活用でもそのまま意識できそうです。

- 人間がすべての差分を均一な熱量で読むのをやめ、**影響範囲（Blast Radius）でメリハリをつける**
- 事後の指摘を減らすために、**仕様定義（Spec）と機械的な制約（ハーネス）**に力を入れる
- コードの見た目だけでなく、**「動作の証拠（Receipts）」**をベースに確認する

今回はまず世の中の議論や事例を整理しましたが、次回はこれを踏まえて**「じゃあ自分の開発環境やワークフローでは具体的にどう仕組み化するか」**（リスク別のTier設計やハーネスの作り方など）を自分なりにまとめてみたいと思います。

皆さんのチームや個人開発では、AIが書いたコードのレビューや確認をどう工夫していますか？よければコメントなどで教えてください。
