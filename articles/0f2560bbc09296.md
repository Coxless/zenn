## 簡単に言うと

GitHub Actionsのランナーに[mise](https://mise.jdx.dev/)をセットアップするcomposite action **setup-mise** を作りました。`action.yml`と`run.sh`の2ファイルだけで完結するので、verifiedなactionしか使えないorganizationでも、自リポジトリにコピーして使えます。

https://github.com/Coxless/setup-mise

## はじめに

最近、ローカルとCIのツールバージョンを揃えるためにmiseを使っています。CIでmiseをセットアップする場合、[jdx/mise-action](https://github.com/jdx/mise-action)を使うのが一般的だと思うのですが、これがverified actionではありません。

organizationのポリシーによっては「GitHub製またはverified creatorのactionのみ許可」という設定になっていることがあり、その環境ではmise-actionが使えませんでした。

また、mise-actionはJavaScript actionなので、中で何をやっているのかがパッと見でわかりづらいという問題もあります。セキュリティレビューを通すにも、ビルド済みの`dist/index.js`を読むのは現実的ではありません。

そこで、以下を満たすcomposite actionを自作しました。

- **コピーして使える**: 2ファイル構成なので、自リポジトリの`.github/actions/`に置くだけで動く
- **透明性が高い**: 全部シェルスクリプトなので、何をやっているか読めばわかる

どちらかというと、このactionを直接参照して使うというよりは（もちろん使ってもらってもOKです）、**各organization内にコピーして動かしてもらう**ことを意識して作っています。

## setup-miseとは

GitHub ActionsのUbuntuランナーにmiseをセットアップするcomposite actionです。主な特徴は以下の通りです。

- miseバイナリのダウンロードとSHA256チェックサム検証
- `mise install`による設定ファイルベースのツールインストール
- miseバイナリとインストール済みツールのキャッシュ（`actions/cache`使用）
- `GITHUB_PATH`へのパス登録（後続ステップでそのままツールが使える）
- 依存はbashと`actions/cache`のみ

### 入力パラメータ

| パラメータ | 説明 | デフォルト |
|---|---|---|
| `version` | インストールするmiseのバージョン | 最新版 |
| `install` | セットアップ後に`mise install`を実行するか | `true` |
| `working_directory` | `mise install`を実行するディレクトリ | `.` |
| `cache` | miseバイナリとツールをキャッシュするか | `true` |
| `log_level` | miseのログレベル | `info` |
| `config_file` | mise設定ファイルのパス（キャッシュキーに使用） | `.mise.toml` |
| `github_token` | レート制限回避のためのGitHubトークン | `github.token` |

## 仕組み

ファイルは`action.yml`と`run.sh`の2つだけです。流れは以下の通りです。

1. **バージョン解決** — `version`未指定なら`https://mise.jdx.dev/VERSION`から最新版を取得
2. **キャッシュ復元** — `actions/cache`でmiseバイナリと`~/.local/share/mise`（インストール済みツール）を復元
3. **ダウンロードと検証** — キャッシュミス時はGitHub Releasesからtarballを取得し、`SHASUMS256.txt`でチェックサムを検証
4. **ツールインストール** — `mise install`で設定ファイルに書かれたツールをインストール
5. **パス登録** — `~/.local/bin`とmiseのshimsを`GITHUB_PATH`に追加

キャッシュキーは`mise-<OS>-<バージョン>-<設定ファイルのハッシュ>`の形式で、設定ファイルを変更すると自動的にキャッシュが再作成されます。

コアの処理はこんな感じです（`run.sh`から抜粋）↓

```bash
echo "Downloading mise ${MISE_TAG}..."
curl -fsSL --header "Authorization: Bearer ${INPUT_GITHUB_TOKEN}" \
  "${BASE_URL}/${TARBALL_NAME}" -o "${WORK_DIR}/${TARBALL_NAME}"
curl -fsSL --header "Authorization: Bearer ${INPUT_GITHUB_TOKEN}" \
  "${BASE_URL}/SHASUMS256.txt" -o "${WORK_DIR}/SHASUMS256.txt"

echo "Verifying checksum..."
grep "${TARBALL_NAME}" "${WORK_DIR}/SHASUMS256.txt" \
  | (cd "${WORK_DIR}" && sha256sum --check)
```

シェルスクリプトなので、レビューする側も「何をダウンロードして、どこに置いて、何を実行するのか」を追いやすいと思います。

## 使い方

### そのまま使う場合

```yaml
steps:
  - uses: actions/checkout@v4

  - uses: Coxless/setup-mise@v1.2.1

  - run: node --version
```

リポジトリの`.mise.toml`に書かれたツールが自動でインストールされ、後続ステップでそのまま使えます。

### コピーして使う場合（おすすめ）

verified actionしか使えない環境では、`action.yml`と`run.sh`を自リポジトリにコピーします。

```
.github/actions/setup-mise/
├── action.yml
└── run.sh
```

ワークフローからはローカルパスで参照します。

```yaml
steps:
  - uses: actions/checkout@v4

  - uses: ./.github/actions/setup-mise
```

ローカルパス参照のactionはポリシーの制限を受けないため、これでverified制限のあるorganizationでもmiseが使えます。

### Gitサブモジュールとして使う場合

コピーの代わりにサブモジュールで取り込む方法もあります。

```bash
git submodule add https://github.com/Coxless/setup-mise .github/actions/setup-mise
```

この場合、`actions/checkout`でサブモジュールも取得するように設定します。

```yaml
- uses: actions/checkout@v4
  with:
    submodules: true

- uses: ./.github/actions/setup-mise
```

### その他のオプション

バージョン固定やキャッシュ無効化もできます。

```yaml
- uses: Coxless/setup-mise@v1.2.1
  with:
    version: '2025.1.0'
    cache: 'false'
```

サブディレクトリの設定ファイルを使う場合↓

```yaml
- uses: Coxless/setup-mise@v1.2.1
  with:
    working_directory: backend
    config_file: .mise.toml
```

## 補足

- 現状、**Ubuntuランナー（`ubuntu-latest`など）のみ対応**です。
- mise-actionにある一部の機能（toolsの直接指定、experimental機能の有効化など）は実装していません。シンプルさを優先しています。
- コピーして使う場合、本家の更新に自動追従はしないので、必要に応じて取り込み直す必要があります。

## おわりに

- verified actionしか使えない環境でもmiseを使いたくて、コピーして使えるcomposite actionを作りました。
- composite action + シェルスクリプトの構成は、透明性が求められる場面と相性がいいと感じています。
- 同じようにorganizationのポリシーで困っている方は、ぜひコピーして使ってみてください。
