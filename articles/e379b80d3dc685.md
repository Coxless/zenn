## はじめに

現在、自分はNext.jsを使って開発しています。next devで開発サーバを立ち上げたときに、ローカルの変更内容が即時反映されるHMR（Hot Module Replacement）はもはや当たり前になっていると思います。
ただ、HMRがどのような仕組みで成り立っているのか理解することなく使っていたので、勉強のためにHMRの仕組みを調べまとめました。

また、調べていく中で開発体験を向上させるTipsがいくつかあったので、それも共有します。

:::message
Next.jsでは、Turbopackを開発環境のビルドツールとして用いているため、今回はTurbopackに特化した内容になっています。
:::

**参考**: [Turbopack | Vercel](https://vercel.com/blog/turbopack)、[API Reference: Turbopack | Next.js](https://nextjs.org/docs/app/api-reference/turbopack)

## HMR（Hot Module Replacement）とは
HMRは、**ページ全体をリロードせずに、変更されたモジュールだけをブラウザ上で差し替える仕組み**です。
(自分は昔全体をビルドして差し替えているのかと勘違いしてました。)

HMRなしでは、全体を再ビルドするため都度ページがフルリロードされ、画面自体がいったん白くなってしまい、フォームの入力内容もスクロール位置もReactのstateも全部吹き飛びます。

HMRがあると以下のメリットがあります：

- **stateが保持される**（カウンターの値やフォーム入力がそのまま）
- **変更が即座に反映される**（ファイル保存 → 数十ms〜数百msで反映）
- **開発のフローが途切れない**

## HMRの全体フロー

Next.js + Turbopackの場合、HMRは以下の5つのステップで動いています。

<!-- 図解はここに挿入（下記参照） -->

### Step 1: ファイル変更の検知

OSのファイルシステム監視API（Linuxなら`inotify`、macOSなら`FSEvents`）を通じて、Turbopackのdevサーバーがファイルの変更を検知します。

### Step 2: インクリメンタルコンパイル（差分ビルド）

Turbopackの内部では、ビルド処理が**関数の依存グラフ**としてモデル化されています。各関数の入出力は「Value Cell（`Vc<…>`）」というデータの最小単位で管理されていて、スプレッドシートのセルのように自動で依存関係が追跡されます。

ファイルが変更されると：

1. そのファイルに対応するValue Cellを「dirty」としてマーク
2. そのCellに依存している関数だけを再実行キューに入れる
3. 再実行後、結果が前回と同じなら、そこから先の再計算はスキップ（**等値カット**）
4. 変更が必要な部分だけが上流に向かって伝播していく

これにより、**アプリがどれだけ巨大でも、HMRの速度は「変更の大きさ」にのみ依存する**ようになります。

### Step 3: WebSocketで更新通知

差分ビルドが完了すると、TurbopackのdevサーバーがWebSocket経由でブラウザ側のHMRクライアントにメッセージを送ります。

```
Server → Browser: "チャンクID xxx が更新されたよ"
```

ブラウザには、Next.jsが注入するHMRランタイム（`__turbopack_hmr__` 系のコード）が常駐していて、このメッセージを受け取る準備ができています。

### Step 4: モジュールの差し替え

HMRクライアントは、更新されたチャンクのURLをfetchで取得し、Turbopackのモジュールランタイムが古いモジュールを新しいものに入れ替えます。

この時点で「**モジュールレベル**」の差し替えが完了します。

### Step 5: React Fast Refreshでコンポーネント更新

ここからはReactの仕事です。Next.jsではHMRの上に**React Fast Refresh**が統合されています。

Fast Refreshは、更新されたモジュールがReactコンポーネントをexportしているかを判定します。

- **コンポーネントのみをexportしている場合** → そのコンポーネントの関数定義だけを差し替えて、**stateを保持したまま**再レンダリング
- **コンポーネント以外もexportしている場合** → そのモジュールと、それをimportしているすべてのモジュールを再実行
- **Reactツリーの外のモジュール場合** → フルリロードにフォールバック

内部的には、Reactのreconciler（Fiber）が`resolveFunctionForHotReloading`という関数を使って、古いコンポーネント参照を新しいものに置き換えています。Hooks（`useState`など）のstateは、Fiberノードに紐づいているため、コンポーネントの関数定義が変わっても保持されます。

## Turbopackのインクリメンタルコンピューテーションを深掘りする

Step 2で触れたインクリメンタルコンパイルについて、もう少し詳しく見てみましょう。

### 従来のアプローチとの違い

ビルドシステムにおけるキャッシュのやり方を比較してみます。

| アプローチ | 粒度 | 例 |
|---|---|---|
| **ファイルレベル** | ファイル単位でキャッシュ | GNU Make |
| **チャンクレベル** | チャンク（バンドル）単位 | webpack |
| **関数レベル** | 関数の入出力単位 | **Turbopack** |

GNU Makeは「出力ファイルが入力ファイルより新しければスキップ」という粗い粒度。webpackはチャンク単位でキャッシュしますが、tree shakingやコード分割のような全体解析を含むと、1ファイルの変更が広範囲に影響します。

Turbopackは**関数の入出力レベル**でキャッシュします。これは、SolidJSのSignalsやスプレッドシートのセル参照に似た「リアクティブ」なモデルです。

### Value Cellの仕組み

Turbopackの内部コードでは、Rustのマクロ（`#[turbo_tasks::function]`）で関数をマークすると、その関数は自動的にキャッシュ対象になります。

```
ファイル読み込み → AST生成 → メタデータ抽出 → チャンク生成 → バンドル出力
    [Vc]         [Vc]         [Vc]            [Vc]          [Vc]
```

各ステップの結果がValue Cell（`Vc`）に格納され、あるCellが別のCellを「読む」と、その依存関係が自動的に記録されます。

重要なのは、**Cellが「読まれた」時点で依存が発生する**ということ。引数として渡されただけでは依存にならず、実際にawaitして値を読んだ瞬間に追跡されます。これにより、不要な再計算をさらに減らしています。

### Aggregation Graph

巨大なアプリでは、Value Cellのグラフが数十万〜数百万ノードになることがあります。このグラフ全体を走査するのは重いので、Turbopackは**Aggregation Graph**という追加のデータ構造を持っています。

Aggregation Graphは、依存グラフを複数のレイヤーで要約したもので、以下のような操作を高速化します：

- サブグラフ内のすべてのdirtyノードの検索
- エラーや警告の集約
- サブグラフの計算完了の待ち合わせ

### Demand-Driven Execution（遅延実行）

Turbopackはdirtyになった関数をすぐには再実行しません。**アクティブなクエリの一部である場合にのみ**再実行します。

開発中の「アクティブなクエリ」= 現在ブラウザで開いているページのHMR接続です。つまり、**開いていないページの再ビルドはスキップされる**ので、余計な計算が走りません。

### File System Cache（永続キャッシュ）

Next.js 16.1からは、Turbopackの計算グラフやValue Cellの結果がディスクに保存されるようになりました。devサーバーを再起動しても、前回のキャッシュからウォームスタートできます。

**参考**: [Inside Turbopack: Building Faster by Building Less | Next.js Blog](https://nextjs.org/blog/turbopack-incremental-computation)

## Fast Refreshが「効かない」パターン

HMR + Fast Refreshは万能ではありません。以下のケースではstateが保持されず、フルリロードになります。

### 1. コンポーネント以外もexportしている

```tsx
// ❌ Fast Refreshがフルリロードになる
export const API_URL = "/api/users";

export default function UserList() {
  // ...
}
```

定数とコンポーネントを同じファイルからexportすると、Fast Refreshはそのファイルを安全に差し替えられないと判断します。**定数は別ファイルに切り出しましょう。**

### 2. クラスコンポーネント

```tsx
// ❌ クラスコンポーネントはstate保持されない
export class Timer extends Component {
  // ...
}
```

Fast Refreshは関数コンポーネント前提で設計されています。クラスコンポーネントの場合はフルリロードになります。

### 3. Hooksの追加・削除

```tsx
// 変更前
export default function App() {
  return <div>Hello</div>;
}

// 変更後（useStateを追加）
export default function App() {
  const [count, setCount] = useState(0); // ← Hooks追加
  return <div>{count}</div>;
}
```

Hooksの追加や削除を伴う変更では、次の1回だけフルリロードになります。その後は通常通りFast Refreshが効きます。

### 4. 高階コンポーネント（HOC）がクラスを返す

```tsx
// ❌ HOCが内部でクラスコンポーネントを返す場合
export const EnhancedComponent = withSomething(MyComponent);
```

HOCの内部実装がクラスコンポーネントを返している場合、Fast Refreshが効きません。

**参考**: [React Fast Refresh | Next.js Docs](https://nextjs.org/docs/architecture/fast-refresh)

## 補足: Server ComponentsやAPI Routeの変更はどう反映される？

HMRは「ブラウザ上で実行中のモジュールを差し替える」仕組みなので、**本来はクライアントサイドの概念**です。ここまで解説したフロー（WebSocket通知 → モジュール差し替え → Fast Refresh）もクライアントサイドの話になります。

ではサーバー側のコードを変更した場合はどうなるのか？Next.jsでは、HMRとは別の仕組みで変更が反映されます。

| 対象 | 仕組み | HMRか？ |
|---|---|---|
| Client Components | HMRランタイム + Fast Refresh | HMRそのもの |
| Server Components | サーバー再コンパイル → RSCペイロード送信 | HMRのWebSocket接続を通知経路として利用しているが、ブラウザ上でモジュール差し替えをしているわけではない |
| API Route | サーバー再コンパイル → 次リクエストで反映 | HMRではない（モジュール無効化・再コンパイル） |

### Server Components（RSC）

Server Componentsのファイルを変更すると、Turbopackがサーバー側で差分コンパイルを行い、更新されたRSCペイロードがブラウザに送られます。クライアント側のReactがそのペイロードをreconcileするため、**Client Componentのstateは保持されます**。これはFast Refreshとは別の仕組みで、RSCプロトコルによるものです。

### API Route（Route Handlers）

API Routeのファイルを変更すると、Turbopackがサーバー側のモジュールを再コンパイルします。ブラウザに表示するUIがないため、**HMR通知自体が発生しません**。次のAPIリクエスト時に、更新後のコードが使われます。

## まとめ

HMRの全体像を改めて整理すると：

1. **ファイル変更検知**（OS API）
2. **インクリメンタルコンパイル**（Turbopackの関数レベルキャッシュ）
3. **WebSocket通知**（devサーバー → ブラウザ）
4. **モジュール差し替え**（HMRランタイム）
5. **React Fast Refresh**（state保持した再レンダリング）

Turbopackの本質は「**変更の影響範囲だけを最小コストで再計算する**」というインクリメンタルコンピューテーションです。アプリの規模が大きくなっても、HMRの速度が劣化しないのはこのアーキテクチャのおかげです。
