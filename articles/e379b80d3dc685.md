## はじめに

Next.jsで`next dev`を実行すると、コードを変更するたびに即座にブラウザに反映されます。もはや当たり前のように使っていますが、この「リアルタイム反映」の仕組みは、**変更するコードの種類によって異なります**。

具体的には、以下の3つに分かれます。

| 対象 | 仕組み | stateの保持 |
|---|---|---|
| **Client Components** | HMR + Fast Refresh | 保持される |
| **Server Components** | HMR（通知経路）+ RSCペイロード再送信 | Client Componentのstateは保持される |
| **API Route等のバックエンド** | requireキャッシュクリア + 再ロード | - （UIなし） |

この記事では、それぞれの仕組みをざっくり解説します。

:::message
Next.jsでは、Turbopackを開発環境のビルドツールとして用いているため、今回はTurbopackに特化した内容になっています。
:::

---

## 共通の起点: ファイル変更の検知

どの種類のコードであっても、起点は同じです。OSのファイルシステム監視API（Linuxなら`inotify`、macOSなら`FSEvents`）を通じて、Turbopackのdevサーバーがファイルの変更を検知します。

その後の処理が、コードの種類によって分岐します。

---

## Client Components: HMR + Fast Refresh

クライアントサイドのコード変更は、**HMR（Hot Module Replacement）+ React Fast Refresh**で反映されます。

### 流れ

1. **差分コンパイル** — Turbopackが変更されたモジュールだけをインクリメンタルにビルド
2. **WebSocket通知** — devサーバーがWebSocket経由でブラウザのHMRクライアントに更新を通知
3. **モジュール差し替え** — HMRランタイムが更新されたモジュールをfetchし、古いモジュールと入れ替え
4. **Fast Refresh** — Reactが変更されたコンポーネントの関数定義だけを差し替え、**stateを保持したまま**再レンダリング

ポイントは、ページ全体をリロードせずに変更されたモジュールだけを差し替えるため、`useState`の値やフォームの入力内容がそのまま保持されることです。

### Fast Refreshが効かないケース

以下の場合はstateが保持されず、フルリロードになります。

- コンポーネントと定数を同じファイルからexportしている場合
- クラスコンポーネントの場合
- Hooksの追加・削除を伴う変更（次の1回のみフルリロード）

**参考**: [React Fast Refresh | Next.js Docs](https://nextjs.org/docs/architecture/fast-refresh)

---

## Server Components: HMR通知経路 + RSCペイロード再送信

Server Componentsの変更は、ブラウザ上でモジュールを差し替えるわけではありません。**サーバー側で再コンパイルし、RSCペイロードとしてブラウザに送り直す**仕組みです。

### 流れ

1. **差分コンパイル** — Turbopackがサーバー側で変更されたServer Componentを再コンパイル
2. **WebSocket通知** — HMRと同じWebSocket接続を使って、ブラウザに「更新があった」ことを通知
3. **RSCペイロード送信** — サーバーが更新されたRSCペイロード（UIのシリアライズされた表現）をブラウザに送信
4. **Reconcile** — クライアント側のReactがRSCペイロードを受け取り、DOMを差分更新

HMRのWebSocket接続は「通知経路」として使われているだけで、ブラウザ上でモジュールの差し替えは行われません。Reactが**RSCプロトコル**に基づいてDOMを更新するため、Client Componentのstateは保持されます。

---

## API Route等のバックエンド: requireキャッシュクリア + 再ロード

API Route（Route Handlers）やMiddlewareなど、ブラウザに表示するUIを持たないバックエンドコードの変更は、HMRとは無関係に処理されます。

### 流れ

1. **差分コンパイル** — Turbopackがサーバー側のモジュールを再コンパイル
2. **モジュールキャッシュの無効化** — 該当モジュールのrequireキャッシュをクリア
3. **次のリクエストで再ロード** — 次にAPIが呼ばれたとき、新しいコードが読み込まれて実行される

ブラウザへのWebSocket通知は発生しません。UIがないため、**次のリクエストが来たタイミング**で更新後のコードが使われます。

---

## まとめ

Next.jsの開発時にコード変更がリアルタイムに反映される仕組みは、変更対象によって3つに分かれています。

- **Client Components** — HMRでモジュールを差し替え、Fast RefreshでReactのstateを保持したまま再レンダリング
- **Server Components** — HMRの通知経路を利用しつつ、RSCペイロードの再送信でDOMを差分更新
- **API Route等のバックエンド** — requireキャッシュクリアで古いモジュールを無効化し、次のリクエスト時に再ロード

どれも起点はTurbopackによるファイル変更検知とインクリメンタルコンパイルですが、そこから先の「変更をどう届けるか」が異なります。
